# Авторизация и безопасность

## Принципы

- У сервиса **нет собственной user base**: ни паролей, ни OAuth-приложения, ни выпуска своих токенов. GitHub — единственный источник истины о личности и правах.
- Пользователь не делает **ничего** сверх уже сделанного `gh auth login`. Никакого браузера.
- Сервис **бесправен** по отношению к GitHub: у него нет ни одного собственного GitHub-токена. Единственный секрет — HMAC-секрет вебхука в env.

## Аутентификация CLI

1. CLI подкладывает `Authorization: Bearer $(gh auth token)` при подключении к стриму — других клиентских запросов и нет ([architecture](01-architecture.md#api)).
2. Сервис проверяет токен **у GitHub, а не у себя**:
   - `GET /user` этим токеном → чей это токен (`github_login`);
   - `GET /repos/{owner}/{repo}` этим же токеном → виден ли пользователю репозиторий.
3. Результат — один из трёх вердиктов: `allowed`, `denied`, `unavailable`.
4. `allowed` и `denied` кэшируются на 300 секунд по умолчанию (ключ: хэш токена + repo), чтобы не упереться в rate limit GitHub API. `unavailable` не кэшируется никогда.

### Трёхзначный вердикт

Одинаковое отображение применяется к обоим запросам в GitHub:

| Ответ GitHub | Вердикт | Кэш |
|---|---|---|
| Оба запроса вернули `200`, `login` — строка | `allowed` | да |
| `401` или `404` | `denied` | да |
| `403` без признаков rate limit | `denied` | да |
| `403` с `x-ratelimit-remaining: 0` или `retry-after` | `unavailable` | нет |
| `429`, любой `5xx`, transport/timeout | `unavailable` | нет |
| Прочий не-`200` | `denied` | да |

`denied` означает подтверждённый отказ: токен или доступ к репозиторию недействителен. `unavailable` означает, что GitHub не смог дать надёжный ответ. Смешивать их нельзя: раньше единичный временный `403` кэшировался как отказ на все 300 секунд, блокировал токен и не оставлял ни одной попытки повтора.

## Точка проверки прав

Доступ к репозиторию проверяется при каждом подключении к `GET /events/stream` — по репо из параметров подписки. Других точек нет: CRUD-endpoint'ов не существует, подписка объявляется самим подключением ([architecture](01-architecture.md#api)).

- `allowed` → подписка открывается; право читать репо = право получать его события.
- `denied` → `403 {"detail":"Repository access denied"}`.
- `unavailable` → `503 {"detail":"GitHub API unavailable"}` и `Retry-After: 5`. Следующее подключение снова реально обращается к GitHub.

Сценарий отзыва прав: разработчика убрали из репозитория — любое следующее (пере)подключение получает `denied`. Остаётся окно уже открытого соединения (оно может жить часами — агент ждёт мёржа); его закрывает сервер, периодически повторяя проверку доступа тем же токеном для живых соединений ([delivery](02-delivery.md#жизненный-цикл-подписки)). При `denied` стрим закрывается. При `unavailable` остаётся открытым, а следующая проверка выполняется через `min(recheck_interval, 30)` секунд: сбой GitHub не должен рвать подписку.

### Переименование, перенос и удаление репозитория

`repo` — точная строка `owner/name`, а не постоянный GitHub repository ID.
Автоматически следовать за переименованием или переносом репозитория сервис не
обещает: payload нового события содержит уже новое `repository.full_name` и не
совпадёт со старой подпиской. Клиент должен переподключиться с новым именем.

После удаления репозитория новая подписка получает `denied`; уже открытый стрим
закрывается при следующей периодической перепроверке прав. Для CI fixture
переименование, перенос и удаление намеренно не автоматизируются: это
разрушительные операции, а поддерживаемый контракт — обновить имя fixture и
перезапустить подписку.

## Вход от GitHub: HMAC

Единственная дверь для событий — `POST /webhook`:

- Org-webhook создаётся с секретом ([github-webhook](04-github-webhook.md#настройка)); секрет лежит в env сервиса.
- Каждый запрос проверяется по `X-Hub-Signature-256` (HMAC-SHA256 тела запроса). Не сошлось — `401`, тело не парсится.

Это отвечает на вопрос «а точно ли это GitHub» без всяких IP-allowlist'ов.

## Модель угроз (кратко)

| Угроза | Защита |
|---|---|
| Подделка событий в `/webhook` | HMAC-подпись |
| Подписка на чужой приватный репо | Проверка `GET /repos/...` токеном подписчика |
| Чтение стрима после отзыва прав | Перепроверка при каждом подключении + периодическая перепроверка живых соединений |
| Кража секретов из сервиса | Красть почти нечего: HMAC-секрет (ротируется пересозданием хука), пользовательские токены не пишутся на диск — живут в памяти в контексте открытого соединения (для периодической перепроверки) и в кэше проверок |
