# CLI

Тонкий клиент к [control plane](01-architecture.md#api). Python + Typer. Аутентификация — токен из `gh auth token`, пользователь не делает ничего ([auth](03-auth.md#аутентификация-cli)).

Целевой пользователь — **AI-агент** (Claude Code, Codex CLI и т.п.): по запросу «babysit this PR» агент запускает `listen`, блокируется в ожидании результата и выходит. Человек в терминале работает так же, просто руками. Отсюда два следствия: [эфемерная модель подписок](#эфемерная-модель-подписок) и [exit-условия](#exit-условия).

## Дистрибуция

Упаковка как **gh-расширение** (паттерн [cli/gh-webhook](04-github-webhook.md#разбор-cligh-webhook)):

```
gh extension install my-org/gh-babysitter
gh babysitter --help
```

Установка и обновления через штатный механизм `gh`, команда живёт в привычном пространстве `gh <...>`. Расширения могут быть скриптами, не только Go-бинарниками, так что Python не помеха (разработчики — целевая аудитория, интерпретатор у них есть).

## Команды

### `listen`

Единственная команда разработчика. Что слушать — объявляется флагами; никаких `subscribe`/`unsubscribe`/`list` и конфиг-файлов не существует:

```
gh babysitter listen -R org/api -E issues                    # все issues репо, бесконечный стрим
gh babysitter listen -R org/api -E issues -n 42              # только issue #42
gh babysitter listen -R org/api -E issues,pull_request       # несколько типов разом
gh babysitter listen -R org/web -n 24 --until merged --timeout 12h  # агентный сценарий
gh babysitter listen -R org/api -E issues | jq '.payload.issue.title'
```

Механика:

1. При старте CLI подключается к `GET /events/stream`, передав подписки параметрами запроса; сервер в этот же момент проверяет доступ к репозиторию ([auth](03-auth.md#точка-проверки-прав)) и начинает стримить.
2. События печатаются как JSON lines в stdout ([формат](02-delivery.md#формат-события)); `--format pretty` — человекочитаемо.
3. Обрыв → реконнект с бэкоффом; подписки переобъявляются из тех же argv — диск не участвует.
4. Ctrl+C / kill / конец сессии агента = unsubscribe: соединение закрылось — подписок больше нет ([delivery](02-delivery.md#жизненный-цикл-подписки)).

Одно соединение покрывает один репозиторий (+ опциональный номер) × несколько типов событий. Ещё один репозиторий или номер — ещё один процесс `listen` в соседнем терминале / сессии агента; группирующих повторяемых флагов сознательно нет.

### Exit-условия

Агенту нужна семантика завершения: команда, которая сама выходит с результатом, удобнее вечного стрима, который надо убивать.

| Флаг | Выход | Код выхода |
|---|---|---|
| `--first-event` | после первого события | 0 |
| `--count N` | после N событий | 0 |
| `--until <status>` | объект достиг статуса — матрица ниже | 0 |
| `--timeout 2h` | время ожидания истекло | 124 |

Без exit-флагов `listen` стримит бесконечно (человеческий режим). Флаги комбинируются: `--until merged --timeout 12h` — «жди мёржа, но не дольше 12 часов».

#### Матрица `--until` (черновик)

Терминальные статусы зависят от типа события:

| `--until` | Тип события | Условие выхода |
|---|---|---|
| `merged` | `pull_request` | `action == "closed"` и `payload.pull_request.merged == true` |
| `closed` | `pull_request`, `issues` | `action == "closed"` (для PR — включая merged) |
| `approved` | `pull_request_review` | `action == "submitted"` и `payload.review.state == "approved"` |
| `changes_requested` | `pull_request_review` | `action == "submitted"` и `payload.review.state == "changes_requested"` |

`--until` требует `-n`: статус есть только у конкретного объекта. Требуемый тип события CLI сам добавляет к подписке, если он не указан в `-E`.

**Poll на границах.** Доставка at-most-once ([delivery](02-delivery.md#принцип-не-слушаешь--не-получаешь)), значит терминальное событие можно пропустить: оно случилось до запуска `listen` или попало в окно реконнекта. Поэтому при `--until` CLI на старте и после каждого реконнекта опрашивает текущее состояние объекта напрямую у GitHub своим же токеном (`gh api repos/{owner}/{repo}/pulls/{number}`); условие уже выполнено → немедленный выход с кодом 0. Стрим — чтобы ждать дёшево, poll на границах — чтобы не зависнуть навсегда.

### `setup` (админская)

Одноразовая команда org-админа — создаёт/обновляет org-webhook с [allowlist](04-github-webhook.md#статический-allowlist) и секретом, используя собственный токен админа. Подробности — в [github-webhook](04-github-webhook.md#настройка).

## Конвенции флагов

Зеркалим `gh` и `gh-webhook`, чтобы не заставлять людей учить новое:

| Флаг | Смысл |
|---|---|
| `-R, --repo org/name` | Репозиторий |
| `-E, --events a,b,c` | Типы событий через запятую (из [меню](04-github-webhook.md#статический-allowlist)) |
| `-n, --number N` | Конкретный issue/PR |
| `--action opened` | Фильтр по action (опционально) |

Exit-флаги (`--until`, `--timeout`, `--count`, `--first-event`) — наши собственные, у `gh` аналогов нет.

### GitHub Enterprise

По умолчанию CLI ходит в `https://api.github.com`. База API определяется первым
заданным источником:

| # | Источник | Тип значения |
|---|---|---|
| 1 | `--api-url` | полный URL |
| 2 | `GH_BABYSITTER_GITHUB_API_URL` | полный URL |
| 3 | `GITHUB_API_URL` | полный URL |
| 4 | `GH_HOST` | хост, URL выводится |
| 5 | `https://api.github.com` | — |

Пустое значение считается незаданным и передаёт очередь следующему источнику.
`GH_HOST` — переменная самого `gh`, поэтому хост из неё разворачивается по его же
правилам: `github.com` → `https://api.github.com`, `<tenant>.ghe.com` →
`https://api.<tenant>.ghe.com`, остальное → `https://<host>/api/v3`.

Сервер настраивается отдельно и читает только `GH_BABYSITTER_GITHUB_API_URL`:
рабочий процесс не должен подхватывать `GH_HOST` из окружения деплоя.

### Таймауты HTTP

| Переменная | По умолчанию | На что влияет |
|---|---|---|
| `GH_BABYSITTER_SERVER_TIMEOUT` | `10` | connect/write/pool для соединения с сервером |
| `GH_BABYSITTER_GITHUB_TIMEOUT` | `10` | все таймауты запросов к GitHub API |

Секунды. Read-таймаут SSE-потока не настраивается и всегда безграничен: соединение
живёт, пока живёт подписка ([delivery](02-delivery.md#жизненный-цикл-подписки)).

## Эфемерная модель подписок

Подписка живёт ровно столько, сколько процесс `listen`: желаемый набор — это аргументы командной строки, серверная регистрация — производная открытого соединения ([delivery](02-delivery.md#жизненный-цикл-подписки)). Состояния нет ни на диске клиента, ни в БД сервера.

Почему так:

- Основной сценарий агентный: подписка нужна на время задачи — «понянчить PR #24» — и мертва после мёржа. Персистентный список таких подписок копил бы мусор из закрытых PR и issues.
- «Память между сессиями» — не-цель: агент каждый раз собирает команду заново из контекста своей задачи. Человеку со стоячим набором подписок хватит alias или скрипта — это забота пользователя, а не инструмента.
- Ноль состояния = систему невозможно привести в несогласованное: и клиент, и сервер после рестарта чисты по построению, всё восстанавливается самим фактом переподключения.
