# ADR: GitHub App вместо org-webhook

Статус: **отклонено** (июль 2026), с явными триггерами пересмотра ниже.

## Контекст

Предложение: построить сервис на базе одного GitHub App, распространяемого как gh-расширение и работающего в двух модах — Сервер (запускает org-админ) и Клиент (запускают разработчики). Клиенты подписываются только на доступные им репозитории; Сервер добавляет репозиторий в инсталляцию App только тогда, когда его запросил хотя бы один клиент.

Предложение распадается на три независимых решения, и судьба у них разная:

1. **Один бинарь, два мода** — принято (и уже было в спеке, см. [ниже](#что-из-предложения-принято)).
2. **GitHub App как основа интеграции** — отклонено.
3. **Подписка сервера на репо по требованию клиентов** — невозможно в желаемом виде, см. разбор.

## Что App дал бы

- Установка через UI GitHub вместо команды `setup`: секрет вебхука, его ротация и доставка событий управляются самим GitHub.
- Installation token: сервер мог бы проверять права клиента сам (`GET /repos/{repo}/collaborators/{username}/permission`), не обращаясь к GitHub токеном пользователя.
- Обязательный фундамент на будущее: write-операции (комментарии, checks) и дистрибуция на чужие организации без App невозможны.

## Почему отклонено

| Аргумент | Суть |
|---|---|
| Ломает бесправность сервиса | Private key приложения даёт серверу права на чтение всех репо инсталляции. Сейчас единственный секрет — HMAC, и красть с сервера нечего ([auth](03-auth.md#принципы)) |
| Клиентам ничего не даёт | Чтобы клиент был «частью App», нужен OAuth/device flow — лишний шаг против принципа «ничего сверх `gh auth login`». Аутентификация токеном из `gh` решает клиентскую сторону лучше и остаётся в любом случае |
| «Подписка по требованию» не работает | GitHub сознательно не даёт приложению расширять собственную инсталляцию (анти-эскалация привилегий): `PUT /user/installations/{id}/repositories/{repo}` требует **user-токен человека с admin-правами**, JWT приложения и installation token не годятся. То есть нужен постоянный админский токен — а это тот же отклонённый вариант «динамической синхронизации» из [github-webhook](04-github-webhook.md#что-отправлять-всё-или-по-фильтрам-подписок), с теми же гонками и дрейфом конфига, плюс private key в нагрузку |
| Меню событий всё равно статическое | Subscribed events у App меняются только в настройках приложения; REST API для этого нет (`PATCH /app/hook/config` меняет лишь URL/секрет). Никакого выигрыша против статического allowlist |

Практический эквивалент, который с App работает — инсталляция «All repositories» с фильтрацией на сервере — по трафику и семантике неотличим от текущего org-webhook, только с более тяжёлым секретом на сервере.

## Что из предложения принято

«Один бинарь, два мода» — уже в спеке: админская `setup` и клиентская `listen` живут в одном gh-расширении ([cli](05-cli.md#команды)). Упаковка туда же серверного процесса (`serve`) — открытый вопрос в [README](../../README.md#открытые-вопросы).

## Триггеры пересмотра

Вернуться к GitHub App, если появится хотя бы одно из:

- write-операции в GitHub: комментарии, checks, labels, статусы;
- больше одной организации или дистрибуция наружу (Marketplace);
- требование проверять права клиентов, не обращаясь их токеном к GitHub API (например, у пользователей fine-grained токены без нужных прав).
