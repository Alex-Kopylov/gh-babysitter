# Доставка событий

## Принцип: не слушаешь — не получаешь

Доставка — это поток в консоль. Сервис пушит события только в **открытые** SSE-соединения; офлайн-клиент события пропускает, и это осознанный принцип дизайна, а не ограничение. Следствия:

- **At-most-once.** Нет очереди, нет replay, нет истории, нет подтверждений доставки.
- События не касаются диска вообще — как и подписки: персистентного состояния у сервиса нет ([architecture](01-architecture.md#модель-данных)).
- Ретраи доставки не нужны: push в открытое соединение либо прошёл, либо соединение мертво — тогда клиент переподключится и переобъявит подписки из своих argv.

## Транспорт: SSE

`GET /events/stream` через `sse-starlette`. Почему SSE, а не WebSocket:

- Поток строго односторонний (сервер → клиент), обратный канал не нужен. `gh-webhook` использует WebSocket потому, что пишет ответ локального сервера обратно в GitHub ([разбор](04-github-webhook.md#разбор-cligh-webhook)) — у нас такого требования нет.
- Работает за NAT и корпоративными прокси, дебажится обычным `curl`.
- Авторизация — обычный заголовок `Authorization: Bearer <token>` при подключении ([auth](03-auth.md)).

Эксплуатационные требования:

- Сервер шлёт keepalive-комментарий (`: ping`) каждые ~30 секунд, иначе прокси рвут «тихие» соединения.
- Если перед сервисом nginx/ingress — на этом роуте `proxy_buffering off`.

## Жизненный цикл подписки

Подписка неотделима от соединения — объявляется при подключении и умирает вместе с ним:

1. `listen` подключается к `GET /events/stream`, перечислив подписки в параметрах запроса ([cli](05-cli.md#listen)); сервер проверяет токен и доступ к репозиторию ([auth](03-auth.md#точка-проверки-прав)) и регистрирует фильтры в памяти.
2. Пока соединение открыто, подписки активны. Само соединение и есть heartbeat — ни lease, ни TTL, ни фоновой чистки: протухать нечему.
3. Соединение закрылось — Ctrl+C, kill, обрыв сети — фильтры удаляются немедленно. Реконнект с бэкоффом на стороне CLI объявляет их заново из argv процесса, и проверка прав при этом проходит заново.

Для долгоживущих соединений (агент ждёт мёржа всю ночь) сервер периодически повторяет проверку доступа тем же токеном и закрывает соединение при отказе ([auth](03-auth.md#точка-проверки-прав)); период — открытый вопрос, порядок минут, согласован с кэшем проверок.

## Формат события

Черновик (открытый вопрос — см. [README](../../README.md#открытые-вопросы)). Каждое событие — одна SSE-message, `data` — JSON-объект:

```json
{
  "ts": "2026-07-12T16:20:00Z",
  "repo": "org/api",
  "event": "issues",
  "action": "opened",
  "number": 42,
  "payload": { "...": "сырой payload GitHub целиком" }
}
```

- Плоские поля дублируют нормализованный кортеж ([architecture](01-architecture.md#нормализация-payload)) — чтобы фильтровать в `jq` без лазанья вглубь payload.
- Идентификатора подписки в событии нет: все фильтры соединения принадлежат одному процессу, а какой сработал — видно по плоским полям. Совпало несколько фильтров — событие приходит один раз.
- CLI печатает `data` как JSON lines в stdout — pipe-friendly ([cli](05-cli.md#listen)).
