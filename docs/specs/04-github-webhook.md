# Webhook на стороне GitHub

## Один org-level webhook

Хук вешается не на каждый репозиторий, а **один на всю организацию**:

- 10 репозиториев покрываются одной настройкой; новые репозитории подхватываются автоматически.
- Payload всегда содержит `repository.full_name`, так что фильтрация по репо остаётся у сервиса ([architecture](01-architecture.md#нормализация-payload)).
- Настраивает org-админ один раз; рядовым разработчикам права на хуки не нужны вообще.

Ограничения GitHub, из-за которых гейтвей и существует: создание хуков требует admin-прав, лимит ~20 хуков на репозиторий/организацию, гранулярность фильтрации — только тип события.

## Что отправлять: всё или по фильтрам подписок?

В конфиге хука есть поле `events` — список **типов** (`issues`, `pull_request`, ...) или `["*"]`. Ни action, ни номер, ни репозиторий внутри org-хука указать нельзя — тонкая фильтрация в любом случае на нашей стороне. Рассмотренные варианты:

| Вариант | Вердикт |
|---|---|
| `["*"]` — всё подряд | Работает, но тащит шум CI: `check_run`, `check_suite`, `status`, `workflow_run` — каждый прогон CI порождает их десятками, это подавляющая часть трафика активного репо |
| Динамическая синхронизация `events` под текущие подписки (`PATCH /orgs/{org}/hooks/{id}`) | Технически один вызов, но операционно дорого: сервису нужен постоянный токен `admin:org_hook` (сейчас он бесправен), появляется гонка «подписка есть — хук ещё не обновлён» и дрейф конфига, требующий сверки. Выигрыш — единицы процентов трафика. **Отклонено** |
| **Статический allowlist** поддерживаемых типов | Настраивается один раз, отсекает шум CI, не требует токенов в сервисе. Конфиг хука самодокументируется: он и есть меню того, на что можно подписаться. **Принято** |

GitHub App-вариант той же идеи («сервер добавляет репо в инсталляцию по требованию клиентов») рассмотрен и отклонён отдельно — [ADR: GitHub App](06-github-app.md).

### Статический allowlist

Черновик меню (открытый вопрос — см. [README](../../README.md#открытые-вопросы)):

```
issues, pull_request, issue_comment, pull_request_review, release
```

Расширение меню = однократное обновление хука админом (или повторный запуск `setup`).

## Настройка

Команда для org-админа, одноразовая ([cli](05-cli.md#setup-админская)):

```
gh babysitter setup --org my-org --url https://hooks.example.com/webhook
```

Она его **собственным** `gh`-токеном создаёт/обновляет org-хук: `content_type: json`, allowlist событий, свежесгенерированный HMAC-секрет (печатается один раз — положить в env сервиса). Токен админа нигде не сохраняется — сервис остаётся бесправным ([auth](03-auth.md#принципы)).

## Разбор cli/gh-webhook

Изучен [cli/gh-webhook v0.2.0](https://github.com/cli/gh-webhook/tree/v0.2.0) (Go, cobra, ~2 файла логики). Команда: `gh webhook forward --events=issues --repo=org/api [--url=...] [--secret=...]`. Механика:

1. `POST /repos/{repo}/hooks` (или `/orgs/{org}/hooks`) создаёт хук **неактивным** и без URL; GitHub возвращает `ws_url`.
2. CLI подключается к websocket с токеном из `gh`, затем активирует хук (`PATCH {active: true}`) — события не текут, пока получатель не готов.
3. События (headers + body) приходят по websocket и POST-ятся на `--url`, а без `--url` печатаются в stdout; ответ локального сервера пишется обратно в websocket.

**Что заимствуем:**

- Конвенции флагов: `-E/--events` списком через запятую и `"*"` как wildcard, `-R/--repo`/`-O/--org` — [cli](05-cli.md#конвенции-флагов).
- stdout по умолчанию, pipe-friendly — ровно наша модель `listen`.
- Упаковка как gh-расширение — дистрибуция и auth-контекст бесплатно.
- Паттерн «одноразовый запуск с токеном админа, который не хранится» — наш `setup`.

**Почему gh-webhook не заменяет гейтвей:** websocket-доставка задумана как «receive **test** events locally»; каждый запуск создаёт отдельный хук, что требует admin-прав (их нет у рядовых разработчиков) и упирается в лимит ~20 хуков (100 подписчиков не влезут физически); фильтрации тоньше типа события нет. Гейтвей — это ровно «один админский хук, много бесправных подписчиков с тонкими фильтрами».

## Локальная разработка

Публичный туннель (smee.io) не нужен: события с настоящей организации заворачиваются в локальный сервис самим gh-webhook:

```
gh webhook forward --org=my-org --events='*' --url=http://localhost:8000/webhook
```
