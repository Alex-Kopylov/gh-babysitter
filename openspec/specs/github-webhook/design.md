# github-webhook — разбор альтернатив

Ограничения GitHub, из-за которых гейтвей и существует: создание хуков требует
admin-прав, лимит ~20 хуков на репозиторий/организацию, гранулярность
фильтрации — только тип события.

## Что отправлять: всё или по фильтрам подписок?

В конфиге хука есть поле `events` — список **типов** (`issues`,
`pull_request`, ...) или `["*"]`. Ни action, ни номер, ни репозиторий внутри
org-хука указать нельзя — тонкая фильтрация в любом случае на нашей стороне.
Рассмотренные варианты:

| Вариант | Вердикт |
|---|---|
| `["*"]` — всё подряд | Работает, но тащит шум CI: `check_run`, `check_suite`, `status`, `workflow_run` — каждый прогон CI порождает их десятками, это подавляющая часть трафика активного репо |
| Динамическая синхронизация `events` под текущие подписки (`PATCH /orgs/{org}/hooks/{id}`) | Технически один вызов, но операционно дорого: сервису нужен постоянный токен `admin:org_hook` (сейчас он бесправен), появляется гонка «подписка есть — хук ещё не обновлён» и дрейф конфига, требующий сверки. Выигрыш — единицы процентов трафика. **Отклонено** |
| **Статический allowlist** поддерживаемых типов | Настраивается один раз, отсекает шум CI, не требует токенов в сервисе. Конфиг хука самодокументируется: он и есть меню того, на что можно подписаться. **Принято** |

GitHub App-вариант той же идеи («сервер добавляет репо в инсталляцию по
требованию клиентов») рассмотрен и отклонён отдельно —
[ADR: GitHub App](#adr-github-app-вместо-org-webhook).

## Разбор cli/gh-webhook

Изучен [cli/gh-webhook v0.2.0](https://github.com/cli/gh-webhook/tree/v0.2.0)
(Go, cobra, ~2 файла логики). Команда:
`gh webhook forward --events=issues --repo=org/api [--url=...] [--secret=...]`.
Механика:

1. `POST /repos/{repo}/hooks` (или `/orgs/{org}/hooks`) создаёт хук
   **неактивным** и без URL; GitHub возвращает `ws_url`.
2. CLI подключается к websocket с токеном из `gh`, затем активирует хук
   (`PATCH {active: true}`) — события не текут, пока получатель не готов.
3. События (headers + body) приходят по websocket и POST-ятся на `--url`, а без
   `--url` печатаются в stdout; ответ локального сервера пишется обратно в
   websocket.

**Что заимствуем:**

- Конвенции флагов: `-E/--events` списком через запятую и `"*"` как wildcard,
  `-R/--repo`/`-O/--org` — [cli](../cli/spec.md).
- stdout по умолчанию, pipe-friendly — ровно наша модель `listen`.
- Упаковка как gh-расширение — дистрибуция и auth-контекст бесплатно.
- Паттерн «одноразовый запуск с токеном админа, который не хранится» — наш
  `setup`.

**Почему gh-webhook не заменяет гейтвей:** websocket-доставка задумана как
«receive **test** events locally»; каждый запуск создаёт отдельный хук, что
требует admin-прав (их нет у рядовых разработчиков) и упирается в лимит ~20
хуков (100 подписчиков не влезут физически); фильтрации тоньше типа события
нет. Гейтвей — это ровно «один админский хук, много бесправных подписчиков с
тонкими фильтрами».

# ADR: GitHub App вместо org-webhook

Статус: **отклонено** (июль 2026), с явными триггерами пересмотра ниже.

## Контекст

Предложение: построить сервис на базе одного GitHub App, распространяемого как
gh-расширение и работающего в двух модах — Сервер (запускает org-админ) и
Клиент (запускают разработчики). Клиенты подписываются только на доступные им
репозитории; Сервер добавляет репозиторий в инсталляцию App только тогда, когда
его запросил хотя бы один клиент.

Предложение распадается на три независимых решения, и судьба у них разная:

1. **Один дистрибутив, три команды** — принято: `listen`, `setup` и `serve`
   (см. [ниже](#что-из-предложения-принято)).
2. **GitHub App как основа интеграции** — отклонено.
3. **Подписка сервера на репо по требованию клиентов** — невозможно в желаемом
   виде, см. разбор.

## Что App дал бы

- Установка через UI GitHub вместо команды `setup`: секрет вебхука, его ротация
  и доставка событий управляются самим GitHub.
- Installation token: сервер мог бы проверять права клиента сам
  (`GET /repos/{repo}/collaborators/{username}/permission`), не обращаясь к
  GitHub токеном пользователя.
- Обязательный фундамент на будущее: write-операции (комментарии, checks) и
  дистрибуция на чужие организации без App невозможны.

## Почему отклонено

| Аргумент | Суть |
|---|---|
| Ломает бесправность сервиса | Private key приложения даёт серверу права на чтение всех репо инсталляции. Сейчас единственный секрет — HMAC, и красть с сервера нечего ([authorization](../authorization/design.md)) |
| Клиентам ничего не даёт | Чтобы клиент был «частью App», нужен OAuth/device flow — лишний шаг против принципа «ничего сверх `gh auth login`». Аутентификация токеном из `gh` решает клиентскую сторону лучше и остаётся в любом случае |
| «Подписка по требованию» не работает | GitHub сознательно не даёт приложению расширять собственную инсталляцию (анти-эскалация привилегий): `PUT /user/installations/{id}/repositories/{repo}` требует **user-токен человека с admin-правами**, JWT приложения и installation token не годятся. То есть нужен постоянный админский токен — а это тот же отклонённый вариант «динамической синхронизации» из [разбора выше](#что-отправлять-всё-или-по-фильтрам-подписок), с теми же гонками и дрейфом конфига, плюс private key в нагрузку |
| Меню событий всё равно статическое | Subscribed events у App меняются только в настройках приложения; REST API для этого нет (`PATCH /app/hook/config` меняет лишь URL/секрет). Никакого выигрыша против статического allowlist |

Практический эквивалент, который с App работает — инсталляция «All
repositories» с фильтрацией на сервере — по трафику и семантике неотличим от
текущего org-webhook, только с более тяжёлым секретом на сервере.

## Что из предложения принято

`listen`, админская `setup` и серверная `serve` живут в одном gh-расширении
([cli](../cli/spec.md)). Отдельного серверного пакета нет.

## Триггеры пересмотра

Вернуться к GitHub App, если появится хотя бы одно из:

- write-операции в GitHub: комментарии, checks, labels, статусы;
- больше одной организации или дистрибуция наружу (Marketplace);
- требование проверять права клиентов, не обращаясь их токеном к GitHub API
  (например, у пользователей fine-grained токены без нужных прав).
