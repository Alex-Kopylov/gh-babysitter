# authorization Specification

## Purpose

Авторизация и безопасность: GitHub — единственный источник истины о личности и
правах, сервис бесправен по отношению к GitHub, единственный секрет —
HMAC-секрет вебхука в env. Принципы и модель угроз — в [design.md](design.md).

## Requirements

### Requirement: Отсутствие собственной user base

Сервис MUST NOT иметь собственной user base: ни паролей, ни OAuth-приложения,
ни выпуска своих токенов. Пользователь MUST NOT делать ничего сверх уже
сделанного `gh auth login` — никакого браузера. Сервис MUST NOT владеть ни
одним собственным GitHub-токеном.

#### Scenario: Аутентификация CLI

- **WHEN** CLI подключается к стриму — других клиентских запросов и нет
  ([event-gateway](../event-gateway/spec.md))
- **THEN** он подкладывает `Authorization: Bearer $(gh auth token)`

### Requirement: Проверка токена у GitHub

Сервис SHALL проверять токен **у GitHub, а не у себя**: `GET /user` этим
токеном → чей это токен (`github_login`); `GET /repos/{owner}/{repo}` этим же
токеном → виден ли пользователю репозиторий.

#### Scenario: Успешная проверка

- **WHEN** оба запроса вернули `200` и `login` — строка
- **THEN** проверка пройдена, сервис знает `github_login` подключившегося

### Requirement: Трёхзначный вердикт

Результат проверки SHALL быть одним из трёх вердиктов: `allowed`, `denied`,
`unavailable`. Одинаковое отображение применяется к обоим запросам в GitHub.
`allowed` и `denied` SHALL кэшироваться на 300 секунд по умолчанию (ключ: хэш
токена + repo), чтобы не упереться в rate limit GitHub API. `unavailable`
MUST NOT кэшироваться никогда: смешивать вердикты нельзя — раньше единичный
временный `403` кэшировался как отказ на все 300 секунд, блокировал токен и не
оставлял ни одной попытки повтора.

#### Scenario: Подтверждённый допуск

- **WHEN** оба запроса вернули `200`, `login` — строка
- **THEN** вердикт `allowed`, результат кэшируется

#### Scenario: Подтверждённый отказ

- **WHEN** GitHub ответил `401`, `404`, `403` без признаков rate limit или
  прочим не-`200`
- **THEN** вердикт `denied` — токен или доступ к репозиторию недействителен;
  результат кэшируется

#### Scenario: GitHub не дал надёжного ответа

- **WHEN** GitHub ответил `403` с `x-ratelimit-remaining: 0` или `retry-after`,
  `429`, любым `5xx`, либо случился transport/timeout
- **THEN** вердикт `unavailable`; результат не кэшируется, следующий запрос
  снова реально обращается к GitHub

### Requirement: Точка проверки прав

Доступ к репозиторию SHALL проверяться при каждом подключении к
`GET /events/stream` — по репо из параметров подписки. Других точек нет:
CRUD-endpoint'ов не существует, подписка объявляется самим подключением
([event-gateway](../event-gateway/spec.md)). Право читать репо SHALL означать
право получать его события.

#### Scenario: allowed

- **WHEN** вердикт проверки — `allowed`
- **THEN** подписка открывается

#### Scenario: denied

- **WHEN** вердикт проверки — `denied`
- **THEN** ответ `403` с телом `{"detail":"Repository access denied"}`

#### Scenario: unavailable

- **WHEN** вердикт проверки — `unavailable`
- **THEN** ответ `503` с телом `{"detail":"GitHub API unavailable"}` и
  заголовком `Retry-After: 5`; следующее подключение снова реально обращается
  к GitHub

### Requirement: Отзыв прав у открытого соединения

Уже открытое соединение может жить часами (агент ждёт мёржа), поэтому сервер
SHALL периодически повторять проверку доступа тем же токеном для живых
соединений ([event-delivery](../event-delivery/spec.md)). Сбой GitHub
MUST NOT рвать подписку.

#### Scenario: Разработчика убрали из репозитория

- **WHEN** права отозваны и клиент (пере)подключается
- **THEN** любое следующее подключение получает `denied`

#### Scenario: Перепроверка живого соединения — отказ

- **WHEN** периодическая перепроверка вернула `denied`
- **THEN** стрим закрывается

#### Scenario: Перепроверка живого соединения — GitHub недоступен

- **WHEN** периодическая перепроверка вернула `unavailable`
- **THEN** стрим остаётся открытым, следующая проверка — через
  `min(recheck_interval, 30)` секунд

### Requirement: Переименование, перенос и удаление репозитория

`repo` — точная строка `owner/name`, а не постоянный GitHub repository ID.
Сервис MUST NOT обещать автоматически следовать за переименованием или
переносом репозитория: payload нового события содержит уже новое
`repository.full_name` и не совпадёт со старой подпиской. Клиент SHALL
переподключиться с новым именем. Для CI fixture переименование, перенос и
удаление намеренно не автоматизируются: это разрушительные операции, а
поддерживаемый контракт — обновить имя fixture и перезапустить подписку.

#### Scenario: Репозиторий переименован или перенесён

- **WHEN** репозиторий сменил `owner/name`
- **THEN** старая подписка перестаёт совпадать с новыми событиями; клиент
  переподключается с новым именем

#### Scenario: Репозиторий удалён

- **WHEN** репозиторий удалён
- **THEN** новая подписка получает `denied`; уже открытый стрим закрывается при
  следующей периодической перепроверке прав

### Requirement: Вход от GitHub — HMAC

Единственная дверь для событий — `POST /webhook`. Org-webhook создаётся с
секретом ([github-webhook](../github-webhook/spec.md)); секрет лежит в env
сервиса. Каждый запрос SHALL проверяться по `X-Hub-Signature-256` (HMAC-SHA256
тела запроса). Это отвечает на вопрос «а точно ли это GitHub» без всяких
IP-allowlist'ов.

#### Scenario: Подпись не сошлась

- **WHEN** подпись отсутствует или не совпала
- **THEN** ответ `401`, тело не парсится
