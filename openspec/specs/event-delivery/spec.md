# event-delivery Specification

## Purpose

Семантика доставки событий: at-most-once пуш в открытые SSE-соединения, без
персистентности, replay и ретраев. Принцип «не слушаешь — не получаешь» —
осознанный принцип дизайна, а не ограничение. Выбор транспорта — в
[design.md](design.md).

## Requirements

### Requirement: At-most-once без replay

Сервис SHALL пушить события только в **открытые** SSE-соединения; офлайн-клиент
события пропускает. Replay, история и повторная отправка потерянного события
MUST NOT существовать; события MUST NOT касаться диска — как и подписки,
персистентного состояния у сервиса нет
([event-gateway](../event-gateway/spec.md)). Потребитель MUST быть идемпотентным.

#### Scenario: Клиент офлайн

- **WHEN** событие приходит, а у клиента нет открытого соединения
- **THEN** клиент это событие пропускает; после переподключения оно не
  восстанавливается

#### Scenario: Повторная доставка GitHub

- **WHEN** GitHub повторно доставляет исходный webhook
- **THEN** сервис обрабатывает его как новую доставку: дубликаты возможны,
  потребитель обязан быть идемпотентным

#### Scenario: Окно реконнекта

- **WHEN** соединение оборвалось и клиент переподключается
- **THEN** клиент переобъявляет подписки из своих argv, но события из окна
  реконнекта не восстанавливаются; ретраев доставки нет

### Requirement: Транспорт SSE

`GET /events/stream` SHALL отдавать поток через SSE (`sse-starlette`).
Сервер SHALL слать keepalive-комментарий (`: ping`) каждые ~30 секунд, иначе
прокси рвут «тихие» соединения.

#### Scenario: Тихое соединение за прокси

- **WHEN** в потоке долго нет событий
- **THEN** клиент получает `: ping` не реже, чем раз в ~30 секунд, и прокси не
  разрывает соединение

#### Scenario: nginx или ingress перед сервисом

- **WHEN** перед сервисом стоит nginx/ingress
- **THEN** на роуте стрима выставляется `proxy_buffering off`

### Requirement: Жизненный цикл подписки

Подписка SHALL объявляться при подключении и SHALL умирать вместе с
соединением. Само соединение и есть heartbeat — lease, TTL и фоновая чистка
MUST NOT существовать: протухать нечему.

#### Scenario: Подключение

- **WHEN** `listen` подключается к `GET /events/stream`, перечислив подписки в
  параметрах запроса ([cli](../cli/spec.md))
- **THEN** сервер проверяет токен и доступ к репозиторию
  ([authorization](../authorization/spec.md)) и регистрирует фильтры в памяти;
  пока соединение открыто, подписки активны

#### Scenario: Соединение закрылось

- **WHEN** соединение закрывается — Ctrl+C, kill, обрыв сети
- **THEN** фильтры удаляются немедленно; реконнект с бэкоффом на стороне CLI
  объявляет их заново из argv процесса, и проверка прав при этом проходит заново

### Requirement: Периодическая перепроверка прав живого соединения

Для долгоживущих соединений (агент ждёт мёржа всю ночь) сервер SHALL каждые
300 секунд по умолчанию повторять проверку доступа тем же токеном
([authorization](../authorization/spec.md)).

#### Scenario: Подтверждённый отказ

- **WHEN** перепроверка вернула вердикт `denied`
- **THEN** сервер закрывает соединение

#### Scenario: GitHub недоступен

- **WHEN** перепроверка вернула вердикт `unavailable`
- **THEN** соединение остаётся открытым, а следующая проверка выполняется через
  `min(recheck_interval, 30)` секунд

### Requirement: Формат события

Каждое событие SHALL быть одной SSE-message, `data` — JSON-объект:

```json
{
  "ts": "2026-07-12T16:20:00Z",
  "repo": "org/api",
  "event": "issues",
  "action": "opened",
  "number": 42,
  "payload": { "...": "сырой payload GitHub целиком" }
}
```

Плоские поля SHALL дублировать нормализованный кортеж
([event-gateway](../event-gateway/spec.md)) — чтобы фильтровать в `jaq` без
лазанья вглубь payload. Идентификатора подписки в событии нет: все фильтры
соединения принадлежат одному процессу, а какой сработал — видно по плоским
полям.

#### Scenario: Совпало несколько фильтров

- **WHEN** несколько фильтров соединения совпали с одним событием
- **THEN** событие приходит один раз

#### Scenario: Вывод CLI

- **WHEN** CLI получает событие
- **THEN** печатает `data` как JSON lines в stdout — pipe-friendly
  ([cli](../cli/spec.md))

### Requirement: Переполнение очереди и событие lag

У каждого `Subscriber` своя bounded-очередь. `POST /webhook` MUST NOT ждать
медленного потребителя и SHALL отвечать `202` с фактическим результатом
fan-out: `matched` — число совпавших подписчиков, `delivered` — скольким
событие добавлено в очередь, `dropped` — у скольких очередь была полной.
Потеря адресна: отставший потребитель SHALL узнавать точное число своих потерь
через событие `lag`.

#### Scenario: Ответ webhook при переполнении

- **WHEN** из 3 совпавших подписчиков у одного очередь полна
- **THEN** ответ `202` с телом `{"matched":3,"delivered":2,"dropped":1}`

#### Scenario: Отставший потребитель возобновил чтение

- **WHEN** потребитель с накопленными потерями снова читает поток
- **THEN** перед следующим ожиданием очереди сервер отправляет
  `event: lag` с `data: {"dropped":4}` — точным числом потерь этого соединения
  с предыдущего `lag`; после отправки счётчик обнуляется

#### Scenario: Реакция CLI на lag

- **WHEN** CLI получает событие `lag`
- **THEN** выводит предупреждение в stderr; потерянные события не
  воспроизводятся
